# DB正規化と移行

現在のコードには、正規化後に [メンバーログイン用の `0004` とオーダー編集権限用の `0005` 移行](member-login.md)、[道具のLINE通知設定用の `0006` 移行](equipment-line-notifications.md)、[スケジュール・出欠用の `0007`〜`0009`、終了時刻用の `0012`、審判手配状況用の `0013` 移行](schedule-management.md)、[ミニゲーム用の `0010` 移行](mini-games.md)、[成績と予定の連携用の `0011` 移行](stats-schedules.md) も必要です。以下の `0003` までの移行を済ませてから、アプリの公開前に未適用のものを順に一度だけ追加適用してください。`0012` まで適用済みなら `0013_schedule_umpire.sql` だけを実行します。週次スケジュールWorkerについてはスケジュールの適用手順を参照してください。

コードと移行SQLを用意した状態です。テスト、ビルド、DB接続、移行SQLの実行は行っていません。

## 保存構造

| テーブル | 内容 |
| --- | --- |
| `app_revisions` | チーム・道具・成績・予定それぞれの更新番号、書き込み識別子 |
| `players` | 選手情報、管理者・オーダー編集権限、名簿・ベンチ・不参加の順序。`sort_order IS NULL` は退団・履歴保管 |
| `team_settings` | チーム名、監督、編集中の試合情報、DH投手、予定ID・集合場所・地図URL・週次更新の記録 |
| `name_options` | 大会名・対戦相手名・場所名の候補と表示順 |
| `lineup_slots` | 打順、守備位置、選手参照 |
| `equipment_items` | 道具、担当選手、メモ、表示順、LINE通知フラグ |
| `stats_games` | 既存の成績保存キー（試合日・試合番号）と連携先の予定ID。予定IDはNULL可・重複不可 |
| `player_game_stats` | 試合・選手ごとの打点等の成績 |
| `plate_appearances` | 試合・選手・打席ごとの結果と得点圏フラグ |
| `schedule_games` | 予定ID、日時、大会名、対戦相手、場所、試合の確定状況、変更番号、直前の時刻・場所、変更者。地図URL列は互換性のため保持 |
| `schedule_responses` | 予定・選手ごとの参加 / 不参加 / 未定、コメント、確認済みの変更番号 |
| `schedule_lineups` | 試合ごとのオーダー形式とDH投手 |
| `schedule_lineup_slots` | 試合・打順ごとの守備位置とスタメン選手 |

選手・試合・成績の参照は外部キーで管理します。選手削除は退団扱いにして、過去成績や道具の担当者IDを残します。成績の試合を削除した場合は、その試合の成績・打席も削除します。予定を削除すると対応する出欠・試合別スタメンも削除しますが、成績は予定IDだけをNULLにして履歴を保持します。連携済み予定の削除では成績revisionも同時に更新します。配列の順序は0始まりの列で保持し、大会・相手・場所候補の重複は統合されます。

試合別保存はスタメン・守備位置・オーダー形式・DH投手だけが対象で、名簿やベンチ・不参加一覧を試合ごとに複製しません。過去試合のスタメン保存は週次更新や関連する保存処理で削除します。予定と出欠の履歴は保持し、過去の予定は20件ずつ追加取得します。

`team_state` / `equipment_state` / `stats_state` は移行時点のJSONを残すバックアップです。移行後のAPIはこれらを読み書きしません。旧成績形式 `{gameDate, players}` と日付だけの試合キーも移行対象です。

## クエリと使用量

以下は正規化導入時のSQL文の数です。実測値ではなく実装から算出しています。`batch()` 一回でも内部のSQL文は複数です。現在の予定とオーダーの連携では、両領域の読取・revision照合・差分保存を追加しています。詳しくは [スケジュール・出欠管理](schedule-management.md) を参照してください。

| 操作 | 変更前 | 変更後 |
| --- | --- | --- |
| チーム・道具の取得 | 2 | 1（認証込み） |
| 成績の取得 | 3（毎回のCREATEを含む） | 1（認証込み） |
| 変更なしの自動更新 | 20秒ごとに2、チーム全体を取得 | 60秒ごとに1、認証とrevisionだけ |
| 差分なしの保存 | チーム・道具2、成績3 | 1、書き込みなし |
| 既存の選手1名・道具1個・打席1つの編集 | チーム・道具2、成績3 | 通常3（比較用読取＋revision更新＋対象テーブル更新） |
| 複数テーブルを変える保存 | JSON全体を更新 | 比較用読取1＋revision更新1＋変更があるテーブルのUPSERT/DELETE各1 |

取得は独立した集約サブクエリを一つのSELECTにまとめ、選手や試合ごとのSELECTループを使いません。成績の保存は変更・削除した試合だけを送信し、DBもその試合だけを読み取ります。成績画面の初回取得は従来どおり全履歴です。チーム・道具の保存時は各領域をまとめて読み、サーバーで差分を計算します。

保存は同一テーブルの変更行をJSONパラメータでまとめ、変更のない行やテーブルを書き換えません。更新番号と一意な書き込み識別子で競合を検出し、変更全体を一つのD1 batchへ入れます。競合時は409、途中の失敗はbatch全体をロールバックします。[D1 batch仕様](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch)

自動保存の650ms待機は維持しています。他端末からの更新反映は最大約60秒になります。保存中の追加入力は次の保存対象に残します。

**正規化前は巨大なJSONでも1行だったため、正規化だけでD1の使用量が減るとは限りません。** D1はSQL文の数ではなく、読み書きした行数とストレージ等を基に使用量を計上します。初回の全件取得や複数行の保存では旧構造より行数が増えます。今回は条件付き取得、更新間隔、試合単位の取得、差分書き込みで増加を抑えています。[D1料金の定義](https://developers.cloudflare.com/d1/platform/pricing/)

## 既存ローカルDBの移行

1. アプリを停止し、`.wrangler/state` を別の場所へバックアップします。移行中に旧APIから書き込むと、移行先へ反映されません。
2. `dist/server/wrangler.json` がなければ、READMEのビルド手順で作成します。
3. 既存の `0000` が適用済みであることを確認し、以下を順に実行します。`0001` と `0002` は既存テーブルがある場合も実行できます。`0003` は一度だけ適用します。

```powershell
npx wrangler d1 execute yg_member_db --local --persist-to="./.wrangler/state" --file="./drizzle/0001_add_equipment_state.sql" --config="./dist/server/wrangler.json"
npx wrangler d1 execute yg_member_db --local --persist-to="./.wrangler/state" --file="./drizzle/0002_add_stats_state.sql" --config="./dist/server/wrangler.json"
npx wrangler d1 execute yg_member_db --local --persist-to="./.wrangler/state" --file="./drizzle/0003_normalize_data.sql" --config="./dist/server/wrangler.json"
```

4. [メンバーログインの適用手順](member-login.md) に従って `0004`・`0005`、[道具のLINE通知設定の適用手順](equipment-line-notifications.md) に従って `0006`、[スケジュールの適用手順](schedule-management.md) に従って `0007`〜`0009` の未適用分を追加適用してから、新しいアプリと週次Workerを公開し、下記を確認します。**既存データを移行する場合は `seed.local.sql` を実行しません。** seedは成績を含めて初期化する開発用です。

本番はバックアップを確保し、書き込みを止めた状態で同じ順序で移行と新APIへの切り替えを行います。旧JSONバックアップは移行後の変更を含まないため、旧コードへ戻すだけでは最新データを復元できません。移行に失敗した場合は、途中まで作られたテーブルにSQLを再適用せず、バックアップから戻して原因を修正します。

## 手元での確認項目

- 移行前後で選手名・順序、打順、DH、不参加、大会・相手候補、道具担当、全試合の成績が一致すること。
- 選手の追加・編集・削除、並べ替え、道具の担当変更、成績の変更が再読み込み後も残ること。
- 一試合の変更・削除が別の試合へ影響しないこと。削除した選手の過去成績がDBに残ること。
- 2画面で同じ領域を変更した際、後から保存した画面で競合になり、先の変更を上書きしないこと。
- 保存中に続けて編集しても次の保存が行われ、変更を元に戻した場合は保存済み表示になること。
- ブラウザのNetworkで自動更新が60秒間隔になり、変更がないと `unchanged: true` が返ること。
- 必要に応じて `PRAGMA foreign_key_check;` とD1の `rows_read` / `rows_written` を確認すること。実際の使用量はデータ量・操作頻度・インデックス更新にも依存します。
